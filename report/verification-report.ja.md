# git 履歴からのシークレット削除：検証レポート

[English](verification-report.en.md)

> このレポートは、ダミーのデータだけで作った検証用リポジトリで、git の履歴からシークレットを削除する手順を実際に動かした記録です。リポジトリの中身、コミットの作者、シークレットの値はすべて架空のものです。

## 1. 結論の要約

**元の手順書のままでは進めないでください。直すべき点を直せば進められます。**

元の手順書をそのまま実行すると、次のことが起きました。

| # | 起きたこと | 影響 |
|---|---|---|
| 1 | `git filter-repo` が `origin` を削除するので、手順4の `git push --force --mirror origin` が失敗する | 手順が途中で止まる |
| 2 | 手順3の `gitleaks detect` は既定のルールだけで動くため、独自形式の値を1件も見つけられない（書き換え前も同じ） | 「消えた」と誤認する |
| 3 | `--replace-text` に生の値だけを書くと、base64 化した値、URL エンコードした値、バイナリファイルや gzip の中の値が残る | 消し残し |
| 4 | `--mirror` push で `refs/pull/*` がすべて拒否され、終了コードが 1 になる | 成否の判断を誤る |
| 5 | `--mirror` push が、clone の後にリモートに作られたブランチを削除する | 他人の作業が消える |

これらを直した修正版の手順（[runbook-revised.ja.md](runbook-revised.ja.md)）を、元の状態に戻してから最初から実行しました。その結果、**すべてのブランチとタグから値が消え**、**ブランチごとのコミット数、件名、マージの構造、merge-base、`version..develop` の件数と件名がすべて書き換え前と一致しました**。機械の作業時間は約30秒でした。

それでも、次のものは git の操作だけでは消せません。

- **GitHub 上の古いコミット**（SHA を指定するとアクセスできる）と、**マージ済み PR の参照**：GitHub サポートへの依頼が必要です。この検証では依頼していません（未確認）
- **PR の本文とコメント、その編集履歴、Actions のログ、Release の添付ファイル、fork**：それぞれ別の対応が必要です

したがって、**最初にやるべきことはシークレットのローテーション**です。履歴の削除は、ローテーションの後に「見つけやすさを下げる」ための作業と考えてください。

## 4. 確認項目の詳細

### A. 消し切れたか

#### 1. 再スキャン — 元の手順書：NG／修正版：OK

**根拠**

- 手順3を書かれたとおり（`gitleaks detect --source . --log-opts="--all" --redact`）に実行すると、既定のルールだけが使われます。書き換え前でも、見つかったのは Kubernetes の Secret マニフェストの汎用ルールの2件だけで、独自形式の値は1件も見つかりませんでした。`detect` サブコマンドは非推奨で、今は `gitleaks git` を使います。
- 独自形式のルール（`scripts/gitleaks/gitleaks.toml`）を使うと、書き換え前は 17 件見つかりました。gitleaks 8.30 は base64 と URL エンコード（パーセントエンコード）を自動で復号して検出します（`decoded:base64`、`decoded:percent` のタグが付く）。ただし、**バイナリファイルの中と gzip の中の値は検出しませんでした**。
- 元の手順書で書き換えた後に、gitleaks（独自ルール付き）と値の直接検索（`scripts/verify/scan_values.py`：全オブジェクトから、生の値、base64、URL エンコード、gzip を展開した中身を探す）で確かめると、次の値が残っていました。

| 残った値 | 原因 |
|---|---|
| base64 化した値 | `replacements.txt` に生の値しか書いていなかった |
| URL エンコードした DB パスワード | 同上 |
| バイナリファイルの中の値 | `--replace-text` はバイナリのファイルを対象にしない（GitHub のドキュメントにも「non-binary files」と書かれている） |
| gzip の中の値 | 圧縮されているので、文字列としては一致しない |

- `.ipynb` の出力セルの値、キーと値が別の行に分かれた JSON の値は、`--replace-text` で消えました。gitleaks の独自ルールで `\s*` を使えば、行をまたいだ値も検出できました。
- 修正版では、エンコードした形も置換リストに入れ、バイナリと gzip はファイルごと削除しました。その結果、gitleaks の検出は 0 件、直接検索でもブランチとタグからは 0 件でした。

**対策**：スキャナーは独自のルールで動かし、そのルールが書き換え前に全件を検出できることを先に確かめる。スキャナーの結果とは別に、既知の値を直接検索する。置換リストには、エンコードした形（base64、URL エンコード、エスケープした形）も入れる。バイナリや圧縮ファイルに含まれる値は、ファイルごと削除するか、作り直したファイルで置き換える。

#### 2. 古い SHA の URL — NG

**根拠**（ログインしていない状態で `curl` を使って確認。`scripts/verify/check_urls.sh`）

| URL の種類 | push の直後 | 約3時間後 |
|---|---|---|
| `github.com/<repo>/commit/<旧SHA>` | 200（24/24） | 200（24/24） |
| `github.com/<repo>/commit/<旧SHA>.patch` | 200（24/24）。差分に値が含まれる | 200（24/24）。差分に値が含まれる |
| `raw.githubusercontent.com/<repo>/<旧SHA>/<path>` | 200。中身に値が含まれる | 200（7/7）。中身に値が含まれる |
| `api.github.com/repos/<repo>/commits/<旧SHA>` | 200 | 200 |
| `github.com/<repo>/blob/<旧SHA>/<path>` | 503（ログインしていない `curl` に一時的に応答しなかった） | 200（7/7）。ページに値が含まれる |

使われていないブランチの先端だけにあったコミットも、ブランチの書き換え後に同じように見られました。約3時間たっても、見られなくなった URL は1つもありませんでした。時間がたてば自然に消える、ということはありません。

**対策**：git の操作だけでは消せません。GitHub のドキュメントによれば、キャッシュされた表示と PR の参照の削除、サーバー側の GC は GitHub サポートが行います。依頼には、リポジトリ名、影響を受ける PR の数、filter-repo が出力する「First Changed Commit(s)」が必要です。サポートは、ローテーションでリスクを抑えられない場合に限って対応する、と書かれています。この検証では依頼していません（未確認）。

#### 4. 古いクローンからの push — 条件付き

| 操作（書き換え前の古いクローンから） | 結果 |
|---|---|
| `git push origin develop` | 拒否（fast-forward でない） |
| `git push --force origin develop`（ruleset で保護） | 拒否（force push 禁止、PR 必須、署名必須。どれか1つでも止まる） |
| `git push --force origin main`（従来の保護） | 拒否 |
| `git push --force origin feature/search`（保護なし） | **成功。古い履歴が戻った** |
| 未 push のブランチを新しいブランチとして push | **成功。古い履歴が戻った** |
| `git pull`（古い develop に新しい develop を取り込む） | 「関係のない履歴」として拒否された。この検証では先頭のコミットも書き換わったためで、先頭のコミットが変わらない場合は**黙ってマージされる**おそれがある |

CI の gitleaks は、値が戻った新しいブランチを検出しました（ワークフローは失敗）。ただし、次の2点に注意してください。

- CI は push の**後**に動くので、push を止めることはできません。
- 古いブランチのコミットにワークフローのファイルが含まれていないと、**ワークフロー自体が動きません**。`feature/search` の force push では何も動きませんでした。

**対策**：書き換えの後しばらくは、ruleset で**すべてのブランチ**（`refs/heads/**`）に対して「force push 禁止」と「作成の制限」をかけ、新しいブランチの作成を一時的に制限する。全員が再クローンしたことを確認する。push protection の独自パターンを使えば push を止められる可能性がありますが、組織向けの機能なので未確認です。

### B. 何が壊れたか

#### 5. ブランチ保護 — 条件付き

- force push するには、保護を外す必要がありました。古いクローンからの force push は、従来のブランチ保護でも ruleset でも拒否されました。
- `gh api` で外し、`gh api` で戻せました。
  - 従来の保護：`DELETE /branches/<b>/protection` で外し、`PUT /branches/<b>/protection` と `POST .../required_signatures` で戻す
  - ruleset：`PUT /rulesets/<id>` で `enforcement` を `disabled` にし、`active` に戻す
- 戻した後の設定は、事前にエクスポートした JSON と一致しました（URL と日時の項目を除く）。`scripts/purge/protection.sh` でエクスポート、解除、復元、比較を行います。
- **署名**：git filter-repo は、**すべてのコミット署名とタグ署名を削除します**。書き換え後の署名付きコミットは 19 件から 0 件になり、署名付きのタグは注釈付きタグになりました。署名を残す方法はありません（GitHub のドキュメントと filter-repo のマニュアルにもそう書かれています）。
- **署名必須のルール**：署名のないコミットは、署名必須のルールでも拒否されます。そのため、force push 禁止のルールだけでなく、署名必須のルールも外す必要があります。戻した後は、すでにあるコミットには影響せず、新しい push にだけルールが適用されます。PR を GitHub 上でマージする運用なら、GitHub がマージコミットに署名するので、そのまま続けられます。
- なお、この検証ではコミットの作者にダミーのメールアドレスを使ったので、署名が GitHub 上で「Verified」と表示されることはありません。手元の `git verify-commit`（SSH 署名）で確認しました。

#### 6. リリースフロー — 元の手順書：NG／修正版：OK

| 比較項目 | 元の手順書 | 修正版（`--prune-empty never`） |
|---|---|---|
| ブランチごとのコミット数 | **2件減った** | 一致 |
| ブランチごとの件名一覧 | **不一致**（「.env を追加」「鍵ファイルを追加」が消えた） | 一致 |
| `version/1.0..develop`、`version/1.1..develop` の件数と件名 | 一致（43件、7件） | 一致 |
| merge-base（件名と日時で比較） | 一致 | 一致 |
| マージの構造（件名、日時、親の数） | 一致 | 一致 |
| ブランチ間の差分（`git diff --stat`） | 削除したファイルの分だけ違う | 同じ（意図どおり） |
| タグ（種類、指す先の件名） | 一致 | 一致 |

ファイルを丸ごと消すと、そのファイルだけを追加したコミットが空になり、filter-repo の既定（`--prune-empty auto`）では消されます。`--prune-empty never` を付けると、空のコミットとして残るので、件数と件名が保たれます。

#### 7. 旧 SHA と新 SHA の対応表 — OK

filter-repo は `.git/filter-repo/` に次のファイルを出力します。

| ファイル | 中身 |
|---|---|
| `commit-map` | 旧 SHA → 新 SHA。削除されたコミットは新 SHA がすべて 0 |
| `ref-map` | ref ごとの旧 SHA → 新 SHA |
| `changed-refs` | 変わった ref の一覧 |
| `first-changed-commits` | 最初に変わったコミット（GitHub サポートへの依頼に使う） |

filter-repo を2回実行した場合でも、`commit-map` は元の SHA から最終的な SHA への対応になっていました。この対応表を使って、submodule の付け替え（項目11）ができました。リリース記録や監査では、記録された旧 SHA を `commit-map` で新 SHA に変換して追跡できます。対応表に値は含まれませんが、旧 SHA があれば GitHub 上の古いコミットを見られるので（項目2）、社内の資料として扱ってください。

#### 8. 実際にはない差分 — 起きる（古いクローンを使ったとき）

古いクローンの `develop` と書き換え後の `version/1.1` を比べると、次のようになりました。

- `git log origin/version/1.1..develop` が **81 件**になった（書き換え前は 7 件）。中身が同じコミットでも、SHA が違うので別のコミットとして数えられる
- `git merge --allow-unrelated-histories` で取り込もうとすると、**12 ファイルが競合**した。強制的にマージすると、**同じ件名のコミットが 73 件重複**した

新しくクローンした状態どうしで比べれば、件数と件名は書き換え前と一致します（項目6）。この現象は、**古いクローンの履歴を新しい履歴に混ぜたとき**に起きます。

#### 9. PR — 条件付き

| PR | 結果 |
|---|---|
| オープン中（3件） | ブランチの force push に追従して、新しい SHA で表示された。コミット数は同じで、マージもできる状態のまま。作り直しは不要だった |
| オープン中で、行コメントがあるもの | 行コメントが「outdated」になった。タイムラインに force push のイベントが残り、旧 SHA へのリンクから古いコミットを見られた |
| 書き換え対象のコミットを含まない PR | 先頭のコミットが署名付きだったので、署名が消えて SHA が変わった。中身の差分は同じ |
| マージ済み（2件） | コミット一覧と差分は、古い `refs/pull/N/head` を使って**古い SHA のまま表示され、値も見えた** |

GitHub のドキュメントは、書き換えの前に、オープン中の PR をマージするかクローズすることを勧めています（古い差分へのコメントが失われるため）。

#### 10. タグと Release — 条件付き

- 軽量タグは軽量タグのまま、注釈付きタグは注釈付きタグのまま書き換わりました。
- 署名付きのタグは、署名が消えて注釈付きタグになりました。
- Release はタグの名前で結び付いているので、消えずに残りました。ソースアーカイブは新しいタグから作られます。
- 添付ファイルは書き換えの対象外なので、削除して作り直す必要があります。

#### 11. submodule — 条件付き

- 親リポジトリを新しくクローンして `git submodule update --init` を実行すると、**古い SHA のまま取得できました**。GitHub がまだ古いオブジェクトを返すためです。
- 一方で、その SHA は書き換え後のどのブランチからもたどれません。GitHub サポートがサーバー側の GC を実行すると、取得できなくなる見込みです（未確認）。
- 直し方：`commit-map` で新しい SHA を調べ、submodule をその SHA に付け替えて、親リポジトリでコミットする。付け替えた SHA が新しい `version/1.1` と一致することを確認しました。ただし、親リポジトリの**過去のコミット**は古い SHA を指したままです。

#### 12. 置き換えの巻き添え — 元の手順書：NG／修正版：OK

`password==>REMOVED_SECRET` のように単語をそのまま置き換えると、次のものまで書き換わりました。

- 関数名と引数名（例：`check_password` が `check_REMOVED_SECRET` に）
- docstring とテスト
- **gitleaks の設定ファイルのルール**（`admin_password` が `admin_REMOVED_SECRET` に）

テストを実行すると1件失敗しました。修正版では、`regex:(ADMIN_PASSWORD\s*=\s*)"password"==>\1"REMOVED_SECRET"` のように、代入している文脈だけを置き換えました。

**差分のレビュー方法**（`scripts/purge/purge_revised.sh review`）：

1. `ref-map` を使って、ブランチとタグの先端ごとに、旧 SHA と新 SHA の間で変わったファイルの一覧を出し、想定したファイルだけかを確かめる
2. 主要なブランチの先端の `git diff -U0` から、**追加された行だけ**を目で確かめる（削除された行には値が含まれるので、画面に出さない）
3. 書き換え後の先端でテストを実行する

### C. 運用

#### 13. 所要時間

この検証用リポジトリ（約100コミット、約 70 KB）での実測値です。

| 作業 | 元の手順書 | 修正版 |
|---|---|---|
| 保護の解除（`gh api`） | 1秒以下 × 2 | 同じ |
| `git clone --mirror` | 1.0秒 | 1秒以下 |
| filter-repo | 0.45秒 + 0.35秒（2回） | 1秒以下（1回） |
| gitleaks | 0.1秒 | 0.1秒 |
| push | 4.2秒 | 3秒 |
| 準備から確認まで全体 | — | 27秒 |

ローカルだけに作った大きなダミーのリポジトリ（`scripts/verify/bench_large.py`、push はしていない）での測定値です。

| コミット数 | パックのサイズ | `--replace-text` | `--invert-paths` | gitleaks |
|---|---|---|---|---|
| 1,000 | 0.5 MB | 0.6秒 | 0.5秒 | 0.2秒 |
| 10,000 | 5.3 MB | 6.0秒 | 3.9秒 | 1.0秒 |
| 50,000（ファイル 5,000） | 29 MB | 61.5秒 | 42.6秒 | 約10秒 |

おおむねコミット数に比例して増え、ファイル数（tree の大きさ）が多いと、さらに長くなります。実際のリポジトリでは、clone と push がネットワークの速さとリポジトリのサイズに左右されます。

#### 14. 凍結時間

- 機械の作業時間は、元の手順書で約1分、修正版で約45秒でした。
- 実際に必要なのは、次の作業を含めた時間です。
  - 書き換え結果の人による確認（項目12）
  - 保護の解除と復元の確認
  - push 後の再スキャン
- 小さなリポジトリでも、**30〜60分の凍結の枠**を取ることを勧めます。
- 修正版のスクリプトは、push の直前にリモートの ref が準備のときから変わっていないかを確かめ、変わっていれば中止します。凍結が守られなかった場合に、他人の push を上書きしないためです。

#### 15. 開発者の手元の作業

試した手順（`scripts` には含めず、[developer-notice.ja.md](developer-notice.ja.md) に記載）：

1. 古いクローンで、未 push のコミットを確かめる（`git log --branches --not --remotes`）
2. 新しくクローンする
3. 新しいクローンに、古いクローンのブランチを `refs/rescue/*` として取り込む
4. 未 push のコミットだけを、新しいブランチに `git cherry-pick <古い基点>..<ブランチ>` で載せ直す
5. `refs/rescue/*` を削除し、`git gc --prune=now` で古いオブジェクトを消す

この手順で、新しいブランチが古い履歴をたどらないことを確認しました（約3秒）。載せ直したコミットそのものに値が含まれていることもあるので（この検証で仕込んだ例がそうでした）、push する前に gitleaks でスキャンします。

#### 16. 使われていないブランチを削除するだけの効果 — 限定的

使われていないブランチ4本（`feature/search`、`feature/legacy-export`、`stg`、`hotfix/old-config`）を削除しただけの状態で調べました。たどれなくなった値は、**それらのブランチの先端にしかなかった2件だけ**でした。それ以外の値は、`main` や `develop` の履歴に残っていました。

さらに、ブランチを削除しても、そのコミットは GitHub 上で SHA を指定すれば見られます（項目2と同じ）。この方法は、ローテーションした後に「見つけにくくする」ための補助的な手段にとどまります。

#### 17. fork — 未確認（ドキュメント上の仕様）

個人アカウントでは、自分のリポジトリを同じアカウントに fork できないので、試せませんでした。GitHub のドキュメントには次のように書かれています。

- 値を含むコミットは、そのコミットを持つ fork では引き続き見られる。fork の所有者に削除を頼むか、fork を削除してもらう必要がある。GitHub サポートは fork を消せず、所有者の連絡先も提供しない
- 同じネットワーク（fork の親子関係）にあるリポジトリの git のデータは、親リポジトリを含むネットワーク内のどのリポジトリからでも、**fork が削除された後でも**アクセスできることがある
- public のリポジトリを private にすると、public の fork は別のネットワークとして public のまま残る

参考：

- https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
- https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/working-with-forks/what-happens-to-forks-when-a-repository-is-deleted-or-changes-visibility

**実際のリポジトリで実施するときの確認方法**：

- `gh api repos/<owner>/<repo>/forks --paginate` で fork の一覧と所有者を確かめる（private の組織リポジトリなら、fork は組織のメンバーのものだけのはず）
- 組織の設定で fork が許可されているかを確かめる
- fork の所有者に、削除または同じ書き換えを依頼する

## 5. よくある懸念への回答

| 懸念 | 起きるか | 対策 |
|---|---|---|
| 値を含むすべてのブランチが変わる。force push できないように保護したブランチがある | **起きる**。最初に変わったコミットより後のすべてのブランチとタグの SHA が変わる。この検証では先頭のコミットに署名があったので、値と関係のないブランチまで変わった。保護（force push 禁止と署名必須）は一時的に外す必要がある | 保護の設定を JSON でエクスポートし、`gh api` で外して、戻した後に差分がないことを確かめる（確認済み）。外している時間は1分程度 |
| 全員がローカルの git を更新する必要がある | **起きる**。古いクローンから push すると、保護のないブランチや新しいブランチで値が戻った | 再クローンを必須にする。未 push の作業は cherry-pick で救う（確認済み）。しばらくはブランチの作成を ruleset で制限する |
| コミット ID が変わり、実際にはない差分が出る。差分のすべてのコミットを説明する必要があるリリースフローで困る | SHA は**変わる**。ただし、新しくクローンした状態どうしなら、`version..develop` の件数と件名、マージの構造、merge-base は**変わらない**（`--prune-empty never` を付けた場合）。実際にはない差分は、古いクローンの履歴を混ぜたときに**起きる** | `--prune-empty never` を付ける。`commit-map` を保存して、旧 SHA を新 SHA に変換できるようにする。古いクローンを使わない |
| develop と version ブランチの履歴をきれいに保つ必要がある | 新しい履歴の中では、構造は保たれる（確認済み） | 古いクローンからのマージを禁止する。`git pull` が「関係のない履歴」と言ったら止めて、再クローンする |
| 実施経験がなく、事故が怖い | 元の手順書には、途中で止まる問題と、黙って消し残す問題があった | まず検証用のリポジトリか、ミラーで試す。修正版の手順は、事前のバックアップ、レビューの段階、push 前の ref の変化チェック、切り戻しの手順（確認済み）を含む |

## 6. 確認できなかったこと、組織の private リポジトリで追加で確認すべきこと

**この検証では確認できなかったこと（未確認）**

- GitHub サポートに依頼した後の結果（キャッシュの削除、`refs/pull/*` の削除、GC）。依頼していない
- fork（個人アカウントでは自分のリポジトリを fork できない）
- 組織単位の ruleset と設定、push protection の独自パターン（組織向けの機能）
- 署名が「Verified」と表示される状態で署名必須のルールを試すこと（コミットの作者がダミーなので不可）
- PR の本文とレビューの編集履歴を、Web 画面から削除すること
- Git LFS を使ったリポジトリ

**組織の private リポジトリで実施するときに、追加で確かめること**

1. 組織の ruleset（リポジトリの設定だけでなく、組織の設定も外す必要があるか）と、バイパスできる人の設定
2. 組織の fork の方針と、既存の fork の一覧
3. 古い SHA の URL が、リポジトリへのアクセス権を持つ人にだけ見えるか（private なら外部には見えないはず）
4. push protection と secret scanning の独自パターンが使えるか（使えれば、古いクローンからの push を止められる可能性がある）
5. Actions のログの保存期間の設定と、ログを削除する権限
6. CI や外部サービスが SHA を記録している場所（デプロイ記録、課題管理、監査ログ）と、`commit-map` での付け替え方
7. リポジトリのサイズで、clone、filter-repo、push にかかる時間（項目13の表で見積もり、事前にミラーで測る）
